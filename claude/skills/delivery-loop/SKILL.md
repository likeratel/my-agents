# 반복 개발 워크플로우

여러 단계에 걸친 기능을 **설계를 먼저 굳히고, 작업 단위 하나씩 계획·구현·검증**하며 완주하는 절차입니다.

## 언제 쓰나

- 하나의 기능이 **여러 작업 단위·여러 배포**로 나뉠 때 (예: 정책 변경 → 마이그레이션 → 신규 도메인 → 공개)
- 순서를 틀리면 **데이터가 깨지거나 되돌리기 어려운** 작업이 섞여 있을 때
- 설계를 사람에게 리뷰받아야 할 때

단발성 수정·버그 픽스·오타 정정에는 쓰지 않습니다. 과합니다.

## 작업 단위

이 문서의 **작업 단위**는 "한 번에 계획하고 구현해서 검증할 수 있는 덩어리"입니다. 이슈 트래커를 쓰면 티켓 하나가
작업 단위이고, 안 쓰면 그냥 번호를 붙인 단계입니다. **티켓은 필수가 아닙니다** — 있으면 링크를 달고, 없으면 순서
번호로 부릅니다.

## 전체 모양

```
0. 설계 (1회)  →  ┌─ 1. 작업 계획 ─ 2. 구현 ─ 3. 리뷰·퀴즈 ─┐
                  └───────── 다음 작업 단위로 반복 ←────────┘
```

`0`은 한 번, `1~3`은 작업 단위마다 반복합니다.

---

## 0단계 · 설계 (1회, 반복 밖)

구현을 시작하기 전에 **현행 분석과 설계를 문서로 확정**합니다. 이 단계를 건너뛰면 반복 도중 설계가 흔들려 앞 단계를
되돌리게 됩니다.

**산출물 위치** — 그 저장소의 문서 규칙을 따릅니다. 규칙이 없으면 어디에 둘지 **묻습니다.** 임의 위치에 파일을
흩뿌리지 않습니다.

**문서 분리** — 한 파일에 전부 담지 않습니다. 주제가 섞이면 논의가 안 됩니다. 권장 분할:

| 문서        | 담는 것                                        |
| ----------- | ---------------------------------------------- |
| `index`     | 한 장 요약 · 확정 사항 · 문서 지도 · 작업 순서 |
| 현행 분석   | 지금 어떻게 동작하는가 (근거는 `파일:라인`)    |
| 설계        | 데이터 · 인터페이스 · 규칙 — 만들 것 전부      |
| 개별 리스크 | 마이그레이션 등 따로 다뤄야 할 주제            |
| 영향·배포   | 범위별 영향 · 배포 순서 · 남은 확인 항목       |

**작업 순서를 반드시 문서에 박습니다.** 각 단계마다:

- **한 줄 요약** — 이 단계가 _왜_ 존재하는가
- **사용자 영향** — 없음 / 일부 / 전체
- **롤백 수단**
- **순서가 강제되는 이유** — 바꾸면 무엇이 깨지는지 구체적으로
- (있으면) 담당 티켓 링크

> 순서 제약은 "그게 자연스러워서"가 아니라 **어기면 깨지는 것**으로만 적습니다. 근거가 약하면 제약이 아닙니다.
> 틀린 근거를 적어두면 나중에 그 근거를 믿고 잘못된 판단을 합니다 — 근거가 흔들리면 즉시 문서를 고칩니다.

**되돌릴 수 없는 단계는 뒤로** 보냅니다. 외부에 공개한 인터페이스, 배포한 SDK, 지운 데이터는 회수되지 않습니다.
안에서 먼저 굴려 확정한 뒤 밖으로 냅니다.

**0단계 종료 조건**: 사람이 문서를 읽고 **설계를 확정**했다.

---

## 1단계 · 작업 계획 (작업 단위마다)

구현 전에 **검증 가능한 목표**로 바꿉니다.

```
1. [무엇을] → 검증: [어떻게 확인]
2. [무엇을] → 검증: [어떻게 확인]
```

계획에 반드시 포함:

- **완료 조건** — 배포 완료가 곧 완료가 아닌 경우가 많습니다. 과도기 호환 코드 제거·문서 갱신처럼 **뒤에 붙는 일**이
  있으면 완료 조건에 명시합니다. 안 적으면 영구히 남습니다.
- **손대는 파일 범위** — 여기 없는 파일을 고치게 되면 멈추고 보고합니다.
- **되돌리는 방법**
- **선행 단계가 끝났는지 확인**

불확실한 점은 **여기서 질문**합니다. 구현 중에 넘겨짚지 않습니다.

## 2단계 · 구현 (작업 단위마다)

- 계획한 범위만 건드립니다. 인접 코드를 "개선"하지 않습니다.
- 설계와 코드가 어긋나면 **설계 문서를 먼저 고치고** 구현합니다. 코드만 바꾸면 문서가 조용히 거짓이 됩니다.
- 계획에 없던 문제를 발견하면 **고치지 말고 보고**합니다. 범위를 넓힐지는 사람이 정합니다.
- 그 저장소의 규칙(코딩 스타일·테스트·커밋·배포)을 따릅니다. 이 워크플로우가 저장소 규칙을 덮어쓰지 않습니다.

**승인 없이 하지 않는 것**: 커밋 · 푸시 · 배포 · 되돌리기 어려운 데이터 변경.

## 3단계 · 리뷰·퀴즈 (작업 단위마다)

구현이 끝나면 **보고 → 퀴즈** 순서로 마무리합니다.

**보고에 담을 것**

| 항목                   | 왜                                         |
| ---------------------- | ------------------------------------------ |
| 무엇을 바꿨나          | 파일·라인 단위로                           |
| 왜 그렇게 했나         | 대안이 있었으면 왜 안 골랐는지             |
| **무엇이 안 바뀌었나** | 영향 없음을 확인한 범위 — 회귀 판단의 근거 |
| 검증한 것 / 못 한 것   | 실패한 테스트는 **실패했다고** 적습니다    |
| 남은 것                | 이 단위에서 의도적으로 뺀 것               |
| 문서 갱신 결과         | 설계 문서와 정본 문서 중 고친 것           |

**퀴즈** — 이번 작업 단위에서 **반드시 알아야 할 핵심**만 3~5문항.

- 정답은 바로 노출하지 말고 접어 둡니다 (`<details><summary>정답 확인</summary>`).
- 각 정답에 한두 줄 해설을 붙여 "왜 그런지"까지 남깁니다.
- 프로젝트 특화 사실보다 **일반적으로 통하는 원리**를 우선합니다.

퀴즈는 형식이 아니라 **인수인계 장치**입니다. "이걸 모르면 다음 사람이 사고 친다"에 해당하는 것만 냅니다.

**3단계 종료 조건**: 사람이 보고를 확인했다. → 다음 작업 단위의 1단계로.

## 사용자 개입 포인트

| 단계         | 개입 유형       | 내용                      |
| ------------ | --------------- | ------------------------- |
| 0. 설계      | **필수 확정**   | 문서 리뷰 후 설계 확정    |
| 1. 작업 계획 | **필수 승인**   | 계획 승인 후 구현 시작    |
| 2. 구현      | 보고            | 범위 밖 문제 발견 시 즉시 |
| 3. 리뷰·퀴즈 | **필수 확인**   | 확인 후 다음 작업 단위로  |
| 커밋 · 푸시  | **필수 승인**   | 요청 없으면 하지 않음     |
| 배포         | **사람이 직접** | 에이전트가 배포하지 않음  |

## 반복 종료

작업 순서 문서의 마지막 단위까지 3단계를 마치면 끝입니다. 마무리로:

- 설계 문서와 실제 구현의 **차이를 문서에 반영**
- 저장소의 **정본 문서**(스키마·API·도메인) 갱신 확인
- 작업 단위 산출물 문서를 보관 위치로 옮길지 판단 — 삭제하지 말고 이동

## 이 워크플로우가 지키려는 것

| 습관                         | 막는 실패                                       |
| ---------------------------- | ----------------------------------------------- |
| 설계를 먼저 확정             | 반복 도중 설계가 흔들려 앞 단계를 되돌리는 일   |
| 순서 제약을 근거와 함께 명시 | 순서를 바꿔도 되는 줄 알고 데이터를 깨뜨리는 일 |
| 완료 조건에 후속 작업 포함   | 과도기 코드가 영구히 남는 일                    |
| "무엇이 안 바뀌었나"를 보고  | 회귀를 놓치는 일                                |
| 되돌릴 수 없는 단계를 뒤로   | 확정 전 스펙을 외부에 내보내는 일               |
| 단위마다 퀴즈                | 맥락이 구현자 머릿속에만 남는 일                |
