# 글로벌 지침

모든 프로젝트에 적용됩니다. 프로젝트에 `CLAUDE.md`나 `PROJECT_RULES.md`가 있으면 **그쪽이 우선**합니다.

코딩 규칙은 `~/.claude/rules/`에 있고 자동으로 읽힙니다. 여기서 반복하지 않습니다.

## 일의 구조

메인 세션이 **요구사항 해석·계획·판단**을 맡고, 손이 많이 가는 일을 서브에이전트에 내립니다.
요구사항을 해석하는 일은 절대 아래로 내리지 않습니다 — 여기서 틀리면 그 아래 작업이 전부 잘못된 전제 위에서
진행되고, 서브에이전트는 전제가 틀렸다는 걸 알 방법이 없습니다.

| 에이전트      | 모델   | 언제                                                  |
| ------------- | ------ | ----------------------------------------------------- |
| `scout`       | sonnet | 어디에 있는지 찾아야 하고, 검색이 여러 번 필요할 때    |
| `implementer` | sonnet | 무엇을 만들지 이미 정해진 뒤의 실제 구현              |
| `reviewer`    | fable  | 구현이 끝나고 커밋·다음 단계로 넘어가기 전            |
| `auditor`     | fable  | 인증·결제·개인정보를 건드렸거나 배포 전               |
| `scribe`      | sonnet | 코드 변경이 끝나고 문서를 맞춰야 할 때                |

## 모호하면 묻는다

계획을 세우다 **분명하지 않은 것 — 해석이 갈리는 요구, 헷갈리는 범위, 확신 없는 전제 — 이 나오면
추측으로 메우지 말고 사용자에게 질문합니다.** 확실하게 인지한 뒤에 시작합니다.

- 질문은 **시작 전, 계획 단계에서** 합니다. 구현 중에 넘겨짚는 것이 최악입니다 — 이미 그 위에 쌓인
  작업까지 같이 무너집니다
- 답하기 쉽게 묻습니다. "어떻게 할까요?"가 아니라 "A로 이해했는데 맞습니까, 아니면 B입니까"처럼
  해석이나 선택지를 제시합니다
- 답이 무엇이든 결과가 같은 것은 묻지 않습니다 — 그건 모호함이 아니라 사소함입니다. 답이 달라지면
  작업이 달라지는 것만 묻습니다
- 질문 없이 세운 전제가 있다면 계획에 **"전제"로 명시**해서 사용자가 확인할 수 있게 합니다

## 서브에이전트를 쓰는 기준

**내리는 게 나을 때**

- 답을 얻기까지 파일을 여러 개 열어야 하는데 정작 필요한 건 결론뿐일 때 (컨텍스트가 실제로 절약됩니다)
- 서로 의존하지 않는 작업이 여럿이라 동시에 돌릴 수 있을 때
- 같은 코드를 다른 눈으로 한 번 더 봐야 할 때 (구현자가 자기 코드를 리뷰하면 놓칩니다)

**직접 하는 게 나을 때**

- 파일 하나를 읽으면 끝나는 일. 위임 왕복이 더 비쌉니다
- 이미 컨텍스트에 있는 내용
- 무엇을 원하는지 아직 확정되지 않은 일

## 모델 라우팅

위임할 때는 모델별 성능 예측이 아니라 **작업의 모양**으로 모델을 고릅니다:

| 작업의 모양                                       | 라우팅                      |
| ------------------------------------------------- | --------------------------- |
| 판단이 아직 남아 있다                             | 위임하지 않음 — 메인이 직접 |
| 기계적·표준적 — 정답이 명확하거나 패턴이 정해짐   | sonnet (바닥)               |
| 미묘하다 — 트레이드오프·동시성·경계조건           | opus                        |
| 마지막 게이트 — 구현 리뷰·보안 감사               | fable 고정, 내리지 않음     |

- **바닥은 sonnet입니다. haiku는 쓰지 않습니다** — 탐색·문서처럼 볼륨이 큰 일도 놓친 호출부 하나가
  외과 원칙을 무너뜨리므로 sonnet 아래로 내려가지 않습니다.
- **성향은 비대칭입니다.** 읽기 작업(탐색·문서)은 애매하면 sonnet에 두고, 쓰기·판단 작업(구현·리뷰)은
  애매하면 위로 올립니다. 틀렸을 때 치르는 비용이 다르기 때문입니다.
- 역할의 기본 모델과 다르게 갈 때는 Agent 호출의 `model` 오버라이드를 씁니다.
  까다로운 구현(동시성·마이그레이션) → `implementer(opus)`.
- **승격은 한 방향입니다.** sonnet → opus → fable. 결과가 불충분하면 한 단계 위 모델로 1회 재시도,
  그래도 안 되면 보고합니다. 같은 모델로 재시도를 반복하지 않고, 강등도 하지 않습니다.
- 위임할 때마다 **한 줄로 라우팅을 밝힙니다**: "탐색 3건 → scout(sonnet) 병렬".
- 서브에이전트는 위 5종만 씁니다. 다른 플러그인이 깔아둔 에이전트 카탈로그는 쓰지 않습니다.

## 위임할 때

지시를 **자족적으로** 씁니다. 서브에이전트는 이 대화를 보지 못합니다. 배경·범위·건드리면 안 되는 것·무엇을
돌려받고 싶은지를 지시 안에 다 넣습니다.

돌아온 결과를 그대로 믿지 않습니다. 특히 "다 됐다"는 보고는 근거를 확인합니다. 테스트가 통과했다고 하면
어떤 명령이 어떤 결과를 냈는지가 보고에 있어야 합니다.

## 외과적 변경

기능 추가든 수정이든 **기존 동작에 영향이 없도록 최소 절개**로 작업합니다.

- 요청받은 변경 외의 동작이 바뀌어서는 안 됩니다. 인접 코드 "개선"을 곁들이지 않습니다
- 다른 동작에 영향이 **불가피하면 작업 전에 반드시 사용자에게 알립니다.** 작업 중에 발견하면 그 지점에서
  멈추고 보고합니다 — "아마 괜찮겠지"로 진행하지 않습니다
- 위임 지시에는 손대도 되는 범위를 명시하고, 보고에는 "기존 동작 영향"을 받습니다

## 문서 산출물

설계·분석·리포트 같은 **산출물 문서는 자립적인 단일 HTML 파일**로 만듭니다. 그림·다이어그램도 전부 HTML —
인라인 SVG 또는 HTML/CSS로 그리고, PNG나 외부 작도 서비스는 쓰지 않습니다.

`~/.claude/templates/document.html`에서 시작하고, 그림은 `diagram-patterns.html`의 패턴을 복사해 씁니다.
`README`·`CHANGELOG`처럼 그 저장소가 이미 마크다운으로 관리하는 **정본 문서는 예외** — 기존 형식을 따릅니다.

자세한 규칙은 `~/.claude/rules/common/documentation.md`에 있습니다.

## 웹 브라우징

gstack의 `/browse` 스킬을 씁니다. `mcp__claude-in-chrome__*` 도구는 쓰지 않습니다.
만든 HTML 문서는 **브라우저로 열어 확인**합니다 — 라이트·다크 양쪽과 좁은 화면을 봅니다.

## 기본 워크플로우

**거의 모든 작업이 `delivery-loop`를 탑니다.** 여러 단위로 나뉘거나 비가역 단계가 섞인 작업은 전체 경로
(설계 → 리뷰 → 확정 → 반복), 한 번에 끝나는 작업은 경량 경로(계획 → 계획 승인 → 구현 → 구현 리뷰)를 탑니다.

예외는 **오타 수정 · 한 줄 픽스 · 코드를 바꾸지 않는 질문 답변**뿐입니다.
