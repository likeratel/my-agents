# 반복 개발 워크플로우

**설계를 먼저 굳히고, 확정된 문서를 채점 기준 삼아 작업 단위를 자율 루프로 완주**하는 절차입니다.

사람 게이트는 양끝에 있습니다 — 시작에서 **무엇을 만들지 서명**하고, 끝에서 **그대로 됐는지 검수**합니다.
사이는 에이전트가 스스로 만들고 검증하며 돌되, 상한과 탈출 조건이 있는 루프입니다.

## 언제 쓰나

**기본으로 탑니다.** 예외는 오타 수정 · 한 줄 픽스 · 코드를 바꾸지 않는 질문 답변뿐입니다.

| 경로 | 언제                                                                  | 앵커 (루프의 채점 기준) |
| ---- | --------------------------------------------------------------------- | ----------------------- |
| 전체 | 여러 작업 단위·여러 배포로 나뉘거나, 순서를 틀리면 되돌리기 어려울 때 | 확정된 설계 문서        |
| 경량 | 한 번에 계획·구현·검증이 끝나는 작업 (버그 픽스, 단일 기능)           | 승인된 계획             |

설계도 계획도 쓸 수 없는 **탐색적 작업**(UX 다듬기, 시안 비교)은 이 루프에 맞지 않습니다 — 앵커가 없으면
판정도 없습니다. 그런 작업은 짧은 반복마다 사람에게 보여주는 쪽이 맞습니다.

## 자율 루프의 3원칙 (두 경로 공통)

1. **앵커는 루프 안에서 고치지 않습니다.** 앵커가 채점 기준인데 루프 안에서 고칠 수 있으면, 구현을 앵커에
   맞추는 대신 **앵커를 구현에 맞춰 "통과"시키는** 자기참조가 됩니다. 앵커의 결함을 발견하면 루프를 멈추고
   보고합니다 — 앵커를 고치는 권한은 사람에게 있습니다.
2. **상한은 같은 단위 2회입니다.** 판정 불통과로 같은 단위를 두 번 다시 만들었는데도 안 되면 멈추고 사람을
   부릅니다. 같은 시도를 세 번 반복하지 않습니다.
3. **판정은 만든 손이 하지 않습니다.** 구현자가 자기 결과를 채점하지 않습니다. 판정은 reviewer가 하고,
   통과 기준은 취향이 아니라 **앵커와의 일치** — 완료 조건의 항목별 충족입니다.

**즉시 탈출 조건** — 다음을 만나면 루프를 돌지 않고 바로 사람에게 갑니다:

- 앵커(설계·계획)의 결함 발견
- 범위 밖 영향 발견 (외과적 변경 원칙)
- 비가역 단계 도달

커밋 · 푸시 · 배포가 사람 승인 사항인 것은 루프와 무관하게 그대로입니다.

## 퀴즈 원칙 — 사람 게이트의 이해 검증

퀴즈는 시험이 아니라 **거울**입니다. 에이전트가 일하고 사람이 서명만 하면 이해가 침식되므로(인지부채),
서명 직전에 서명하는 사람의 이해를 확인합니다.

- **급소만 냅니다**: 순서 제약의 이유 · 롤백 수단 · 영향 범위 · 의도적으로 뺀 것 · 무엇이 안 바뀌었나.
  모르면 나중에 사고 나는 것만 — **낼 급소가 없으면 내지 않습니다**
- **객관식 2~4지선다**로 냅니다. 오답 선택지는 그럴듯한 오해로 구성합니다 — 정답이 뻔하면 검증이
  아니라 요식입니다
- **상한**: 전체 경로 한 사이클에 총 8문항 이하. 게이트별 상한은 각 단계에 있습니다. 상한이 없으면
  퀴즈를 도장 찍듯 넘기게 되고, 그 순간 이 장치는 목적을 잃습니다
- **오답은 블로킹이 아니라 신호입니다.** 정답·해설·관련 문서 위치를 바로 제시합니다. 문서가 불명확한
  신호면 문서를 고치고, 이해 격차면 해설로 메웁니다. 서명을 막지는 않되, 오답이 나온 영역은 리뷰에서
  한 번 더 짚습니다

## 경량 경로 (단일 작업 단위)

같은 원리를 계획 하나로 접습니다. 게이트는 양끝 그대로입니다.

1. **계획** — 무엇을 · 손대는 파일 범위 · **완료 조건**("검증: 어떻게 확인" 형식) · **영향 범위**(바뀌면
   안 되는 기존 동작) · 되돌리는 방법. 모호한 점은 여기서 질문해 확정하고, 질문 없이 세운 전제는 "전제"로
   명시합니다
2. **계획 승인** — 사람이 서명해야 루프가 시작됩니다. 계획에 순서 제약·영향 범위 같은 급소가 있으면
   서명 전 **퀴즈 최대 1문항**
3. **자율 루프** — 구현 → 리뷰·판정(계획과 일치하는가) → 불통과면 수정 후 재판정, 같은 단위 최대 2회
4. **최종 확인** — 바뀐 것 · 안 바뀐 것 · 검증 결과를 보고하고, 급소가 있으면 **퀴즈 최대 2문항** 뒤
   사람이 확인해야 종료합니다

퀴즈는 급소가 있을 때만 냅니다 — 사소한 변경이면 생략합니다 (「퀴즈 원칙」).

## 작업 단위

**작업 단위**는 "한 번에 구현해서 판정받을 수 있는 덩어리"입니다. 이슈 트래커를 쓰면 티켓 하나가 작업
단위이고, 안 쓰면 그냥 번호를 붙인 단계입니다. **티켓은 필수가 아닙니다** — 있으면 링크를 달고, 없으면
순서 번호로 부릅니다.

## 전체 모양 (전체 경로)

```
A. 설계 문서 → B. 설계 리뷰 → C. 퀴즈 → D. 확정
                  사람          사람      사람
        │
        ▼
  ┌ 단위마다: 구현 → 리뷰·판정(앵커 일치?) ─ 불통과 → 수정 후 재판정 (최대 2회) ┐
  │            통과 → 진행 보고 남기고 다음 단위로 (승인 대기 없음)             │
  └──────────────────────────────────────────────────────────────────────┘
        │ 마지막 단위 통과
        ▼
E. 최종 리뷰 — 사람
```

`A~D`는 한 번, 루프는 단위마다, `E`는 한 번입니다.

# A. 설계 문서

구현 전에 **현행 분석과 설계를 문서로** 만듭니다. 이 문서가 확정되면 루프 전체의 채점 기준이 되므로,
여기서의 빈틈은 루프가 그대로 물려받습니다.

**산출물 위치** — 그 저장소의 문서 규칙을 따릅니다. 규칙이 없으면 어디에 둘지 **묻습니다.** 임의 위치에
파일을 흩뿌리지 않습니다.

**산출물 형식** — 자립적인 단일 HTML 파일입니다. 그림·표·다이어그램도 전부 HTML(인라인 SVG 또는 CSS)로
그립니다. `~/.claude/templates/document.html`에서 시작하고, 자세한 규칙은
`~/.claude/rules/common/documentation.md`에 있습니다. 단계 순서·데이터 이동·상태 전이는 글보다 그림이
빠릅니다.

**문서 분리** — 한 파일에 전부 담지 않습니다. 주제가 섞이면 논의가 안 됩니다.

| 문서        | 담는 것                                        |
| ----------- | ---------------------------------------------- |
| `index`     | 한 장 요약 · 확정 사항 · 문서 지도 · 작업 순서 |
| 현행 분석   | 지금 어떻게 동작하는가 (근거는 `파일:라인`)    |
| 설계        | 데이터 · 인터페이스 · 규칙 — 만들 것 전부      |
| 개별 리스크 | 마이그레이션 등 따로 다뤄야 할 주제            |
| 영향·배포   | 범위별 영향 · 배포 순서 · 남은 확인 항목       |

**계획은 이 문서에 흡수됩니다.** 루프에는 단위별 계획 단계가 따로 없습니다. 예전에 계획이 담던 것을
작업 순서가 다 담아야 하며, **여기 없는 것은 루프가 판정할 수 없습니다.** 각 단계마다:

- **한 줄 요약** — 이 단계가 _왜_ 존재하는가
- **완료 조건** — "검증: 어떻게 확인" 형식. 루프의 판정 기준이므로 실제로 검증 가능해야 합니다.
  과도기 호환 코드 제거·문서 갱신처럼 뒤에 붙는 일도 완료 조건에 명시합니다 — 안 적으면 영구히 남습니다
- **손대는 파일 범위** — 여기 없는 파일을 고치게 되면 루프를 탈출해 보고합니다
- **사용자 영향** — 없음 / 일부 / 전체
- **롤백 수단**
- **순서가 강제되는 이유** — 바꾸면 무엇이 깨지는지 구체적으로
- (있으면) 담당 티켓 링크

> 순서 제약은 "그게 자연스러워서"가 아니라 **어기면 깨지는 것**으로만 적습니다. 근거가 약하면 제약이
> 아닙니다. 틀린 근거를 적어두면 나중에 그 근거를 믿고 잘못된 판단을 합니다.

**되돌릴 수 없는 단계는 뒤로** 보냅니다. 외부에 공개한 인터페이스, 배포한 SDK, 지운 데이터는 회수되지
않습니다. 안에서 먼저 굴려 확정한 뒤 밖으로 냅니다.

# B. 설계 리뷰

사람이 읽고 논의하는 단계입니다. 문서는 **리뷰 자료이자 개발 산출물**이므로 둘 다 되게 씁니다.

리뷰에 올리기 전 스스로 점검:

- 한 장 요약만 읽어도 무엇을 왜 하는지 전달되는가
- **결정된 것과 미결인 것이 구분**되어 있는가 — 미결을 결정처럼 적지 않았는가
- 단위마다 완료 조건이 "검증: 어떻게 확인" 형식으로 있는가 — 루프가 이걸로 판정합니다
- 순서 제약마다 "어기면 무엇이 깨지는지"가 있는가
- 사람이 확인해 줘야 할 항목이 따로 모여 있는가

리뷰에서 결정이 바뀌면 **문서를 먼저 고치고** 다시 올립니다. 대화로만 합의하고 문서를 안 고치면 다음
사람은 낡은 문서를 믿습니다.

# C. 퀴즈 — 확정 전 이해 검증

확정은 이 워크플로우에서 가장 무거운 서명입니다 — 이후 루프가 이 문서만 보고 자율로 돕니다. 서명하기
전에, **서명하는 사람이 설계를 실제로 이해했는지** 퀴즈로 확인합니다.

- **3~5문항**, 설계의 급소만: 순서 제약의 이유("어기면 무엇이 깨지는가") · 롤백 수단 · 영향 범위 ·
  의도적으로 뺀 것. 형식과 오답 처리는 「퀴즈 원칙」을 따릅니다
- 문서에 남길 때는 정답을 접어 둡니다 (`<details><summary>정답 확인</summary>`). 각 정답에 한두 줄 해설
- **퀴즈에서 막히면 문서가 불명확하다는 신호입니다** — 답을 알려주고 넘어가는 게 아니라 B로 돌아가
  문서를 고칩니다

# D. 확정

사람이 설계를 확정합니다. 확정 시점에 문서에 남길 것:

- **확정 사항 목록** — 무엇이 정해졌는가
- **의도적으로 뺀 것** — 왜 안 하는지까지
- **남은 미결과 담당** — 누가 언제 확인하는가

확정과 함께 루프가 시작됩니다. 확정 후에 설계를 바꾸려면 A로 돌아갑니다 — 루프 안에서 슬쩍 바꾸지
않습니다.

# 구현 루프 (작업 단위마다)

## 구현

- 앵커가 정한 범위만 건드립니다. 인접 코드를 "개선"하지 않습니다
- 계획에 없던 문제를 발견하면 **고치지 말고 루프를 탈출해 보고**합니다. 범위를 넓힐지는 사람이 정합니다
- **설계와 현실이 어긋나는 것을 발견하면 즉시 탈출합니다.** 문서를 고쳐 맞추지 않습니다 — 앵커 수정은
  사람의 권한입니다 (3원칙 1)
- 그 저장소의 규칙(코딩 스타일·테스트·커밋·배포)을 따릅니다. 이 워크플로우가 저장소 규칙을 덮어쓰지
  않습니다

## 리뷰 · 판정

reviewer가 깨끗한 컨텍스트에서 두 가지를 봅니다:

1. **결함** — 정확성 · 회귀 · 에러 경로 (reviewer의 평소 기준 그대로)
2. **앵커 일치** — 이 단위의 완료 조건을 항목별로 대조해 충족 여부 판정

판정은 **통과 / 불통과**로 명시하고, 불통과는 어떤 항목이 왜 미달인지 함께 적습니다.
불통과 → implementer가 고치고 재판정. **같은 단위 2회 상한** — 넘으면 멈추고 사람을 부릅니다.

## 진행 보고 (통과 시)

단위가 통과할 때마다 남기되, **승인을 기다리지 않고** 다음 단위로 갑니다:

| 항목                   | 왜                                         |
| ---------------------- | ------------------------------------------ |
| 무엇을 바꿨나          | 파일·라인 단위로                           |
| **무엇이 안 바뀌었나** | 영향 없음을 확인한 범위 — 회귀 판단의 근거 |
| 검증 결과              | 어떤 명령이 어떤 출력을 냈는지             |
| 배운 것                | 다음 사람이 모르면 사고 칠 한두 가지       |

"배운 것"이 예전 단위별 퀴즈의 인수인계 기능을 대신합니다. 이 보고의 누적이 E의 리뷰 자료가 됩니다 —
사람은 흘러가는 보고를 지켜보다 이상하면 언제든 개입할 수 있습니다.

# E. 최종 리뷰 — 사람

마지막 단위가 통과하면 사람이 전체를 검수합니다. 검수 자료:

- **진행 보고 누적** — 단위별 변경·검증 내역
- **배운 것 모음** — 단위별 한두 가지씩
- **설계-구현 차이** — 원칙적으로 없어야 하며(루프가 보장), 탈출을 거쳐 사람이 승인한 변경이 있다면
  그 목록
- 저장소의 **정본 문서**(스키마·API·도메인) 갱신 확인
- 작업 단위 산출물 문서를 보관 위치로 옮길지 판단 — 삭제하지 말고 이동

## 이 워크플로우가 지키려는 것

| 습관                         | 막는 실패                                       |
| ---------------------------- | ----------------------------------------------- |
| 설계를 먼저 확정             | 반복 도중 설계가 흔들려 앞 단계를 되돌리는 일   |
| 서명 게이트 앞 퀴즈          | 이해하지 못한 채 서명하는 일 — 인지부채         |
| 퀴즈 상한 (사이클 총 8문항)  | 퀴즈 자체를 도장 찍듯 넘기게 되는 일            |
| 앵커를 루프 안에서 안 고침   | 문서를 구현에 맞춰 "통과"시키는 자기참조        |
| 판정 기준 = 앵커 일치        | "만족했다"는 주관으로 루프가 끝나는 일          |
| 같은 단위 2회 상한           | 같은 실수를 비싸게 반복하는 일                  |
| 판정과 구현의 분리           | 자기 채점                                       |
| 진행 보고 누적               | 최종 리뷰에 부담이 한꺼번에 몰리는 일           |
| 순서 제약을 근거와 함께 명시 | 순서를 바꿔도 되는 줄 알고 데이터를 깨뜨리는 일 |
| 되돌릴 수 없는 단계를 뒤로   | 확정 전 스펙을 외부에 내보내는 일               |
