# 반복 개발 워크플로우

**설계를 먼저 굳히고, 작업 단위 하나씩 계획·구현·검증**하며 완주하는 절차입니다.

## 언제 쓰나

**기본으로 탑니다.** 예외는 오타 수정 · 한 줄 픽스 · 코드를 바꾸지 않는 질문 답변뿐입니다.

경로는 두 가지입니다:

| 경로 | 언제                                                                     | 모양               |
| ---- | ------------------------------------------------------------------------ | ------------------ |
| 전체 | 여러 작업 단위·여러 배포로 나뉘거나, 순서를 틀리면 되돌리기 어려울 때    | A~C 한 번 + 1~5 반복 |
| 경량 | 한 번에 계획·구현·검증이 끝나는 작업 (버그 픽스, 단일 기능 추가)         | 아래 「경량 경로」  |

## 경량 경로 (단일 작업 단위)

A~C를 별도 문서 없이 **계획 하나로 접습니다.** 접는 것은 문서량이지 게이트가 아닙니다 — 승인 없이
구현하지 않는 것은 똑같습니다.

1. **계획** — 무엇을 · 손대는 파일 범위 · 완료 조건 · **영향 범위**(바뀌면 안 되는 기존 동작) · 되돌리는 방법.
   모호한 점은 **여기서 질문해 확정**하고, 질문 없이 세운 전제는 계획에 "전제"로 명시합니다
2. **계획 리뷰** — 사람이 승인해야 구현을 시작합니다
3. **구현** — 계획한 범위만. 범위 밖 영향을 발견하면 멈추고 보고합니다
4. **구현 리뷰** — 무엇이 바뀌었고 **무엇이 안 바뀌었는지**, 검증 결과와 함께 보고합니다. 사람이 확인해야 종료

퀴즈는 인수인계 가치가 있을 때만 냅니다. 버그 픽스 하나에 퀴즈는 형식주의입니다.

## 작업 단위

**작업 단위**는 "한 번에 계획하고 구현해서 검증할 수 있는 덩어리"입니다. 이슈 트래커를 쓰면 티켓 하나가 작업
단위이고, 안 쓰면 그냥 번호를 붙인 단계입니다. **티켓은 필수가 아닙니다** — 있으면 링크를 달고, 없으면 순서 번호로
부릅니다.

## 전체 모양

```
A. 문서 작성 및 설계
B. 문서 · 설계 리뷰
C. 확정
        │
        ▼
   ┌─ 1. 작업 계획 ─ 2. 계획 리뷰 ─ 3. 구현 ─ 4. 구현 리뷰 ─ 5. 퀴즈 ─┐
   └───────────────── 다음 작업 단위로 반복 ←─────────────────────┘
```

`A~C`는 한 번, `1~5`는 작업 단위마다 반복합니다.

**리뷰는 별도 단계입니다.** 만든 사람이 곧바로 다음으로 넘어가지 않고, 사람이 보고 통과시켜야 진행합니다. 리뷰를 앞
단계에 접어 넣으면 "만들면서 검토했다"가 되어 게이트가 사라집니다.

# A. 문서 작성 및 설계

구현 전에 **현행 분석과 설계를 문서로** 만듭니다. 이 단계를 건너뛰면 반복 도중 설계가 흔들려 앞 단계를 되돌리게
됩니다.

**산출물 위치** — 그 저장소의 문서 규칙을 따릅니다. 규칙이 없으면 어디에 둘지 **묻습니다.** 임의 위치에 파일을
흩뿌리지 않습니다.

**산출물 형식** — 자립적인 단일 HTML 파일입니다. 그림·표·다이어그램도 전부 HTML(인라인 SVG 또는 CSS)로
그립니다. `~/.claude/templates/document.html`에서 시작하고, 자세한 규칙은
`~/.claude/rules/common/documentation.md`에 있습니다. 설계 문서는 사람이 읽고 논의하는 물건이라
**흐름과 순서를 그림으로 보여주는 것이 특히 중요합니다** — 단계 순서, 데이터 이동, 상태 전이는 글보다 그림이 빠릅니다.

**문서 분리** — 한 파일에 전부 담지 않습니다. 주제가 섞이면 논의가 안 됩니다.

| 문서        | 담는 것                                        |
| ----------- | ---------------------------------------------- |
| `index`     | 한 장 요약 · 확정 사항 · 문서 지도 · 작업 순서 |
| 현행 분석   | 지금 어떻게 동작하는가 (근거는 `파일:라인`)    |
| 설계        | 데이터 · 인터페이스 · 규칙 — 만들 것 전부      |
| 개별 리스크 | 마이그레이션 등 따로 다뤄야 할 주제            |
| 영향·배포   | 범위별 영향 · 배포 순서 · 남은 확인 항목       |

**작업 순서를 반드시 문서에 박습니다.** 각 단계마다:

- **한 줄 요약** — 이 단계가 _왜_ 존재하는가
- **사용자 영향** — 없음 / 일부 / 전체
- **롤백 수단**
- **순서가 강제되는 이유** — 바꾸면 무엇이 깨지는지 구체적으로
- (있으면) 담당 티켓 링크

> 순서 제약은 "그게 자연스러워서"가 아니라 **어기면 깨지는 것**으로만 적습니다. 근거가 약하면 제약이 아닙니다. 틀린
> 근거를 적어두면 나중에 그 근거를 믿고 잘못된 판단을 합니다 — 근거가 흔들리면 즉시 문서를 고칩니다.

**되돌릴 수 없는 단계는 뒤로** 보냅니다. 외부에 공개한 인터페이스, 배포한 SDK, 지운 데이터는 회수되지 않습니다. 안에서
먼저 굴려 확정한 뒤 밖으로 냅니다.

# B. 문서 · 설계 리뷰

사람이 읽고 논의하는 단계입니다. 문서는 **리뷰 자료이자 개발 산출물**이므로 둘 다 되게 씁니다.

리뷰에 올리기 전 스스로 점검:

- 한 장 요약만 읽어도 무엇을 왜 하는지 전달되는가
- **결정된 것과 미결인 것이 구분**되어 있는가 — 미결을 결정처럼 적지 않았는가
- 순서 제약마다 "어기면 무엇이 깨지는지"가 있는가
- 사람이 확인해 줘야 할 항목이 따로 모여 있는가
- 약어·용어 정리와 이해도 퀴즈가 있는가

리뷰에서 결정이 바뀌면 **문서를 먼저 고치고** 다시 올립니다. 대화로만 합의하고 문서를 안 고치면 다음 사람은 낡은
문서를 믿습니다.

# C. 확정

사람이 설계를 확정합니다. 확정 시점에 문서에 남길 것:

- **확정 사항 목록** — 무엇이 정해졌는가
- **의도적으로 뺀 것** — 왜 안 하는지까지
- **남은 미결과 담당** — 누가 언제 확인하는가

확정 후에 설계를 바꾸려면 A로 돌아갑니다. 반복(1~5) 안에서 슬쩍 바꾸지 않습니다.

# 1. 작업 계획 (작업 단위마다)

구현 전에 **검증 가능한 목표**로 바꿉니다.

```
1. [무엇을] → 검증: [어떻게 확인]
2. [무엇을] → 검증: [어떻게 확인]
```

계획에 반드시 포함:

- **완료 조건** — 배포 완료가 곧 완료가 아닌 경우가 많습니다. 과도기 호환 코드 제거·문서 갱신처럼 **뒤에 붙는 일**이
  있으면 완료 조건에 명시합니다. 안 적으면 영구히 남습니다.
- **손대는 파일 범위** — 여기 없는 파일을 고치게 되면 멈추고 보고합니다.
- **되돌리는 방법**
- **선행 작업 단위가 끝났는지 확인**

불확실한 점은 **여기서 질문**합니다. 구현 중에 넘겨짚지 않습니다.

# 2. 계획 리뷰

사람이 계획을 승인해야 구현을 시작합니다. 계획 리뷰가 잡아내는 것:

- 범위가 너무 넓거나 좁은가
- 완료 조건에 **후속 작업이 빠졌는가**
- 검증 방법이 실제로 성패를 가르는가 — "동작하는지 본다"는 검증이 아닙니다
- 선행 조건이 정말 끝났는가

승인 없이 구현하지 않습니다.

# 3. 구현

- 계획한 범위만 건드립니다. 인접 코드를 "개선"하지 않습니다.
- 설계와 코드가 어긋나면 **설계 문서를 먼저 고치고** 구현합니다. 코드만 바꾸면 문서가 조용히 거짓이 됩니다.
- 계획에 없던 문제를 발견하면 **고치지 말고 보고**합니다. 범위를 넓힐지는 사람이 정합니다.
- 그 저장소의 규칙(코딩 스타일·테스트·커밋·배포)을 따릅니다. 이 워크플로우가 저장소 규칙을 덮어쓰지 않습니다.

**승인 없이 하지 않는 것**: 커밋 · 푸시 · 배포 · 되돌리기 어려운 데이터 변경.

# 4. 구현 리뷰

무엇을 했는지 사람에게 보고합니다.

| 항목                   | 왜                                         |
| ---------------------- | ------------------------------------------ |
| 무엇을 바꿨나          | 파일·라인 단위로                           |
| 왜 그렇게 했나         | 대안이 있었으면 왜 안 골랐는지             |
| **무엇이 안 바뀌었나** | 영향 없음을 확인한 범위 — 회귀 판단의 근거 |
| 검증한 것 / 못 한 것   | 실패한 테스트는 **실패했다고** 적습니다    |
| 남은 것                | 이 단위에서 의도적으로 뺀 것               |
| 문서 갱신 결과         | 설계 문서와 정본 문서 중 고친 것           |

계획과 달라진 게 있으면 **달라졌다고 먼저 말합니다.** 결과만 보여주고 넘어가지 않습니다.

# 5. 퀴즈

이번 작업 단위에서 **반드시 알아야 할 핵심**만 3~5문항.

- 정답은 바로 노출하지 말고 접어 둡니다 (`<details><summary>정답 확인</summary>`).
- 각 정답에 한두 줄 해설을 붙여 "왜 그런지"까지 남깁니다.
- 프로젝트 특화 사실보다 **일반적으로 통하는 원리**를 우선합니다.

퀴즈는 형식이 아니라 **인수인계 장치**입니다. "이걸 모르면 다음 사람이 사고 친다"에 해당하는 것만 냅니다.

퀴즈까지 마치면 다음 작업 단위의 1번으로 돌아갑니다.

## 사용자 개입 포인트

| 단계              | 개입 유형       | 내용                      |
| ----------------- | --------------- | ------------------------- |
| B. 문서·설계 리뷰 | **필수 리뷰**   | 읽고 논의 · 결정 변경     |
| C. 확정           | **필수 확정**   | 확정해야 반복 시작        |
| 2. 계획 리뷰      | **필수 승인**   | 승인해야 구현 시작        |
| 3. 구현           | 보고            | 범위 밖 문제 발견 시 즉시 |
| 4. 구현 리뷰      | **필수 확인**   | 확인해야 다음 작업 단위로 |
| 커밋 · 푸시       | **필수 승인**   | 요청 없으면 하지 않음     |
| 배포              | **사람이 직접** | 에이전트가 배포하지 않음  |

## 반복 종료

작업 순서 문서의 마지막 단위까지 5번을 마치면 끝입니다. 마무리로:

- 설계 문서와 실제 구현의 **차이를 문서에 반영**
- 저장소의 **정본 문서**(스키마·API·도메인) 갱신 확인
- 작업 단위 산출물 문서를 보관 위치로 옮길지 판단 — 삭제하지 말고 이동

## 이 워크플로우가 지키려는 것

| 습관                         | 막는 실패                                       |
| ---------------------------- | ----------------------------------------------- |
| 설계를 먼저 확정             | 반복 도중 설계가 흔들려 앞 단계를 되돌리는 일   |
| 리뷰를 별도 단계로           | "만들면서 검토했다"로 게이트가 사라지는 일      |
| 순서 제약을 근거와 함께 명시 | 순서를 바꿔도 되는 줄 알고 데이터를 깨뜨리는 일 |
| 완료 조건에 후속 작업 포함   | 과도기 코드가 영구히 남는 일                    |
| "무엇이 안 바뀌었나"를 보고  | 회귀를 놓치는 일                                |
| 되돌릴 수 없는 단계를 뒤로   | 확정 전 스펙을 외부에 내보내는 일               |
| 단위마다 퀴즈                | 맥락이 구현자 머릿속에만 남는 일                |
