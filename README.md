# my-agents

내 AI 에이전트 설정 모음입니다. 스킬·지침·설정을 한 저장소에서 관리하고, 각 에이전트가 읽는 위치로 **심볼릭 링크**를
겁니다. 원본이 여기 있으니 어느 기계에서든 클론하고 `./install.sh` 한 번이면 됩니다.

## 구조

저장소 안의 폴더명은 **대상 위치와 같습니다.** `.claude/`의 내용이 `~/.claude/`로 갑니다.

```
my-agents/
├── .claude/
│   ├── agents/               → ~/.claude/agents/ (항목별 링크)
│   │   └── scout · implementer · reviewer · auditor · scribe
│   ├── skills/               → ~/.claude/skills/ (항목별 링크)
│   │   └── delivery-loop/
│   ├── rules/                → ~/.claude/rules (폴더 통째 링크)
│   │   ├── common/           모든 언어 공통 규칙
│   │   └── typescript/       TS·JS 파일에만 붙는 규칙
│   ├── CLAUDE.md             → ~/.claude/CLAUDE.md
│   └── PROJECT_TEMPLATE.md   → ~/.claude/PROJECT_TEMPLATE.md
├── install.sh                ← 심볼릭 링크 설치 (idempotent)
└── README.md
```

에이전트가 늘어나면 `.codex/` · `.cursor/` 처럼 최상위에 그 에이전트의 폴더를 추가하고 `install.sh`에 링크 규칙을
더합니다.

**링크 방식이 두 가지인 이유**: `skills/`는 다른 스킬 모음과 한 디렉토리를 공유하므로 항목별로 링크합니다. `rules/`는
트리 전체가 우리 것이라 폴더 하나로 링크합니다.

## 설치

```bash
git clone git@github.com-personal:likeratel/my-agents.git ~/development/my-agents
cd ~/development/my-agents && ./install.sh
```

**기존에 같은 이름의 실제 파일·폴더가 있으면 건드리지 않고 건너뜁니다** — 다른 설정 모음을 덮어쓰지 않기 위함입니다.
건너뛴 항목은 실행 결과에 이름이 찍히니 직접 확인해서 옮기거나 지우면 됩니다.

## 에이전트

메인 세션이 요구사항 해석·계획·판단을 맡고, 손이 많이 가는 일을 서브에이전트에 내리는 구조입니다.
**요구사항 해석은 아래로 내리지 않습니다** — 거기서 틀리면 그 아래 작업이 전부 잘못된 전제 위에서 진행되는데,
서브에이전트는 전제가 틀렸다는 걸 알 방법이 없습니다.

| 에이전트      | 모델   | 무엇                                          | 권한       |
| ------------- | ------ | --------------------------------------------- | ---------- |
| `scout`       | haiku  | 파일·심볼·패턴이 어디 있는지 찾아서 위치 보고 | 읽기 전용  |
| `implementer` | sonnet | 정해진 계획대로 코드 작성·수정, 테스트        | 읽기·쓰기  |
| `reviewer`    | opus   | 결함·회귀·설계 이탈 찾기                      | 읽기 전용  |
| `auditor`     | opus   | 보안 감사 — 시크릿, 입력 검증, 인가, 노출     | 읽기 전용  |
| `scribe`      | haiku  | README·CHANGELOG·주석 등 문서                 | 읽기·쓰기  |

싼 모델은 **입구가 아니라 말단**에 둡니다. 탐색·문서처럼 파일을 많이 열지만 결론만 필요한 일에 haiku를 쓰면
메인 컨텍스트가 실제로 가벼워집니다. 반대로 요구사항을 싼 모델에게 먼저 요약시키는 구조는 아낄 토큰도 없고
가장 비싼 오류가 나는 자리에 가장 약한 모델을 놓는 셈이라 쓰지 않습니다.

리뷰가 두 종류인 이유는 보는 것이 다르기 때문입니다. `reviewer`는 "이 코드가 틀리게 도는 입력이 있는가"를,
`auditor`는 "공격자가 이걸로 무엇을 할 수 있는가"를 봅니다. 한 에이전트에 둘 다 시키면 대개 앞쪽만 봅니다.

## 스킬

| 스킬            | 무엇                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `delivery-loop` | 설계 → 리뷰 → 확정 → (계획 → 계획 리뷰 → 구현 → 구현 리뷰 → 퀴즈) 반복. 단계가 많고 순서를 틀리면 되돌리기 어려운 작업용 |

## 규칙

`rules/`는 모든 프로젝트에 깔리는 글로벌 규칙입니다. `common/`은 언어와 무관하게 항상 적용되고, `typescript/`는
frontmatter의 `paths`로 TS·JS 파일에만 붙습니다.

| 파일                        | 무엇                                                        |
| --------------------------- | ----------------------------------------------------------- |
| `common/coding-style.md`    | 불변성, 파일 분할 기준, 에러 처리, 입력 검증                |
| `common/git-workflow.md`    | 커밋 메시지 포맷, PR 작성 절차                              |
| `common/security.md`        | 커밋 전 보안 체크리스트, 시크릿 관리                        |
| `typescript/*.md`           | 위 규칙의 TS·JS 구현 — 스타일·패턴·보안·테스트              |

`PROJECT_TEMPLATE.md`는 프로젝트별 `PROJECT_RULES.md`를 새로 쓸 때 베끼는 템플릿입니다. 글로벌 규칙에 넣기엔
프로젝트 고유한 내용(배포 명령, 팀 컨벤션, 자주 나는 이슈)이 갈 자리입니다.

## 공개 저장소입니다

회사 코드·사내 경로·서비스명·티켓 번호·시크릿은 **넣지 않습니다.** 스킬은 어느 프로젝트에서나 통하도록 범용으로
씁니다. 프로젝트 고유 규칙은 그 저장소의 설정 파일에 두고, 스킬은 "그 저장소 규칙을 따른다"고만 적습니다.
